## What Dark Zenith will be (per DESIGN.md)

An Elixir/Phoenix application that serves a fully-functional RPM (dnf) package repository:

- Phoenix renders all web pages (LiveView) and repository metadata (`repomd.xml`, `primary.xml.gz`, etc.).
- RPM files themselves live in Backblaze B2; clients are 302-redirected to time-limited signed URLs (default 30 min). The app server never streams RPM bytes.
- Three top-level surfaces share one core domain: **Web UI (LiveView)**, **REST API (JSON)**, and the **RPM repo endpoint** consumed by `dnf` at `/repos/:slug/...`.

### Planned stack

| Layer | Technology |
| --- | --- |
| Language / framework | Elixir + Phoenix (LiveView) |
| Database | PostgreSQL (all metadata, including generated repomd blobs) |
| Object storage | Backblaze B2 (S3-compatible) |
| Background jobs | Oban (metadata regeneration, B2 cleanup, preview cleanup, email delivery) |
| Session auth | `mix phx.gen.auth` (bcrypt) |
| API auth | Bearer with API keys (prefix `dzak_`) or short-lived session tokens (`dzst_`); Basic (API key as password) on repo-serving endpoints |
| Email | Swoosh, adapter selected by `MAIL_ADAPTER` (default `zepto`; `smtp`, `local` also supported) |

## Architectural decisions worth knowing before editing the spec

These come up repeatedly in DESIGN.md and tend to constrain new changes:

- **Pure-Elixir RPM header parser** for metadata extraction. The system `rpmkeys`/`rpmsign`/`gpg` tools are only used for integrity verification and signing, not parsing.
- **Metadata is generated by an Oban job, never inline at request time.** Repo endpoints serve from a `metadata_revision`/`source_revision` cache and return `503 metadata_not_ready` (with `Retry-After: 5`) when the cache is behind. The one exception: repository creation synchronously generates empty metadata and writes the cache row (`source_revision = 0`) in the creation transaction, so new empty repos serve valid metadata immediately.
- **Token storage**: secrets (API keys `dzak_`, session tokens `dzst_`) are stored as `HMAC-SHA-256(SECRET_KEY_BASE, full_token_string)` in lowercase hex. Plaintext is shown to the user exactly once. Web uploads carry no bearer token: upload intents are unguessable UUID database resources scoped to their creator. Collaborator invitations carry no token; they convert by normalized-email match at account creation or confirmed account email change.
- **B2 storage keys** are deterministic and sanitized; `name`/`version`/`release`/`arch` must match `^[A-Za-z0-9._+~-]+$` and `epoch` must be an integer in the unsigned 32-bit range.
- **Error format differs by surface**: repo-serving endpoints consumed by dnf (`/repos/:slug/repodata/...`, `.rpm` downloads, `RPM-GPG-KEY`, `dark-zenith.repo`) return bare plain-text error-code bodies (e.g. `metadata_not_ready`); `/api/v1/...` uses the JSON `{"error": {...}}` envelope; web UI routes render HTML.
- **GPG private keys** are stored AEAD-encrypted under a key derived from `SECRET_KEY_BASE`; rotating it requires setting `PREVIOUS_SECRET_KEY_BASE` (an Oban job re-encrypts rows) or existing keys are stranded and fail closed. Key replacement and enabling `sign_rpms` on a non-empty repo trigger per-package re-sign jobs guarded by a `transition_id`.
- **Repository deletion** is a hard delete in one DB transaction; B2 object cleanup is a separate idempotent Oban job with up to 20 attempts. Same retry/visibility policy applies to metadata regen and email delivery.
- **Bootstrap admin** via `ADMIN_EMAIL` / `ADMIN_PASSWORD` env vars on first boot only (since `REGISTRATION_ENABLED` defaults to `false`).

When proposing a change that touches any of these areas, check DESIGN.md first — the spec is detailed and frequently has an explicit rule for the case you're considering.
